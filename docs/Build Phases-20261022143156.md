# Build Phases

The full build plan for the travel baseball SaaS. It merges the four planning docs (Initial Research, Initial Schema, Potential Planning Phases, Season Archiving) into one sequence, fixes the places where they disagree, and rewrites the implementation notes to match this codebase and Laravel best practices.

## 0. Ground Truth: What the Codebase Actually Is

The earlier docs assume Livewire. This app is not Livewire. Every phase below targets the stack that is actually installed:

| Concern                          | Installed                                                                |
| -------------------------------- | ------------------------------------------------------------------------ |
| Framework                        | Laravel 13, PHP 8.5                                                      |
| Frontend                         | Inertia v3 + React 19 + TypeScript, Tailwind v4, Radix/shadcn components |
| Routing to frontend              | Wayfinder (`@/actions/*`, `@/routes/*`), no hardcoded URLs               |
| Auth                             | Fortify (registration, email verification, 2FA already wired)            |
| Tests                            | Pest 5                                                                   |
| Static analysis                  | Larastan level 7                                                         |
| Dev DB / queue / cache / session | SQLite / database / database / database                                  |

Translations from the old docs:

- "Livewire component" → Inertia page in `resources/js/pages` + a resource controller + a Form Request.
- "Dual-listbox Livewire feature" → React component calling the server with `useHttp` and optimistic updates (Inertia v3).
- "`OrgSignup` Livewire component" → Fortify registration (`App\Actions\Fortify\CreateNewUser`) followed by an org-creation step.

Conventions already in the code that new code must follow:

- Models use attribute-based config: `#[Fillable([...])]` and `#[Hidden([...])]`, plus a `casts()` method and `@property` PHPDoc blocks (see `app/Models/User.php`).
- Business operations live in `app/Actions` (Fortify's actions set the pattern: one class, one public method).
- Validation lives in Form Requests under `app/Http/Requests/<Area>/`.
- Controllers are grouped by area under `app/Http/Controllers/<Area>/`.

## 1. Decisions That Resolve Conflicts Between the Docs

Settle these before writing migrations. Each one names the conflict and the recommended answer.

### 1.1 `team_player` gets a `season_id`, locked to the team's season

_Potential Planning Phases_ says the roster pivot needs `season_id`. _Season Archiving_ says it doesn't. **Add it**, because a player may be on only one team per season (decided). That rule spans two tables, so a unique index can't enforce it unless the roster row carries the season. With `season_id` on the row, `unique(season_id, player_id)` makes a second team in the same season impossible, even under concurrent requests.

The usual objection is that the copy can drift from the team's real season. Two things prevent that:

- A **composite foreign key** `(team_id, season_id)` → `teams(id, season_id)`, backed by a `unique(id, season_id)` index on `teams`. MySQL rejects any roster row whose season doesn't match its team.
- `teams.season_id` is **immutable** after creation. It's left out of `#[Fillable]` and the update Form Request. Moving a team to another season isn't a feature; rollover creates new teams.

`AddPlayersToTeam` sets `season_id` from the team. It's never accepted from the client.

### 1.2 One active season per org is enforced by the schema, not a boolean

`seasons.is_active` with "only one per org" is a rule MySQL can't enforce (it has no partial unique indexes). Two concurrent rollovers could leave two active seasons.

**Use `organizations.active_season_id`** (nullable FK → `seasons`, `nullOnDelete`). There is then exactly one active season by construction. `Season::isActive()` becomes a comparison, not a column. Drop `is_active` from `seasons`.

### 1.3 The season filter is not a global scope

_Season Archiving_ puts a session-driven global scope on `Team`. That silently changes every team query, including jobs, exports, the rollover itself (which needs to read the _old_ season's teams), and console commands, where the session is absent or stale. Best practice is to reserve global scopes for truly universal constraints (tenancy, soft deletes).

**Put the season in the URL for season-scoped pages** (`/seasons/{season}/teams`) and query through the relationship (`$season->teams()`). The navbar "Current Season ▼" switcher just navigates to the same page under another season. This makes pages bookmarkable, keeps two browser tabs on two seasons from fighting over one session value, and makes the active season the default landing target. "Archived" seasons are simply ones that are not `active_season_id`.

### 1.4 Tenancy is a global scope, but it never reads the session directly

Tenancy is the one place a global scope is the right tool. But `session('current_org_id')` inside a scope breaks in queued jobs, console commands, and tests. The scope reads from a request-scoped `CurrentOrganization` service instead (details in Phase 1), and the org ID is propagated to jobs with `Context::addHidden()`.

### 1.5 The current org persists on the user, not just in the session

The docs reference `$user->latest_organization_id` but never define it, and the rollover sample uses `auth()->user()->organization_id`, which contradicts the "no `organization_id` on users" rule. **Add `users.current_organization_id`** (nullable FK, `nullOnDelete`) so the last-used org survives logout. Middleware validates membership on every request. A stale or forged value never grants access.

### 1.6 "Guardian" is not an org role

_Initial Schema_ lists `guardian` as an `organization_user.role`. Guardians already have their own table with a nullable `user_id`. Two sources of truth for "is this person a parent" will diverge. **`organization_user.role` is staff only: `Owner`, `Admin`, `Coach`.** A parent's access comes from a claimed `guardians` row (`guardians.user_id`), checked by policies.

### 1.7 Every tenant-owned row has `organization_id`, including `submissions`

_Initial Research_ says almost every table needs `organization_id`. _Initial Schema_ leaves it off `submissions`. Add it, so the tenant scope applies uniformly. Pure pivots (`team_player`, `guardian_player`) don't need it: they are reached only through scoped parents, and route bindings are scoped (Phase 1).

### 1.8 IDs: auto-increment + authorization, slugs for public URLs

_Initial Schema_ floats UUIDs to stop people guessing URLs. Unguessable IDs are not access control; the tenant scope and policies are. **Keep `$table->id()`.** Public pages use slugs. If opaque IDs are wanted later for shareable links, add `HasUlids` to that one model.

### 1.9 Divisions are org-global; teams carry the season

Confirmed by both docs. `divisions` has no `season_id`, so rollover can reuse `division_id` as-is.

Divisions carry **age rules** (decided): `max_age` (10 for "10U") and an optional `min_age`. The date a player's age is measured on changes every year, so it lives on the season as `age_cutoff_on` (for example, May 1, 2026 for Spring 2026). A player's **league age** is their age on that date. The suggested division is the one with the smallest `max_age` that is still ≥ that age. The app only _suggests_ a division: admins can always roster a kid in another division, because playing up is common.

### 1.11 Production runs on MySQL

Decided. What that means for the build:

- **Run tests on MySQL in CI**, not only SQLite. Composite FKs, collations, JSON behavior, and unique-violation error codes differ between the two, and Phase 5 depends on catching unique violations.
- The default `utf8mb4_0900_ai_ci` collation compares case-insensitively, so `unique(organization_id, email)` on guardians is already case-insensitive. Emails are still **lowercased on write** (a model mutator) so matching in PHP gives the same answer.
- MySQL allows several `NULL`s in a unique index, so `unique(team_id, jersey_number)` permits any number of players without a jersey number.
- MySQL creates an index for each foreign key automatically. Don't add duplicate single-column indexes on FK columns.
- `json` columns work as-is. Encrypted columns use `text`.

### 1.12 Platform admins exist and bypass the tenant scope only on an audited path

Decided: we (the platform) need a super-admin. It's built as a separate surface, not a flag that turns the tenant scope off:

- `users.is_platform_admin` (bool, default false). It is **not** in `#[Fillable]`, and it's set only by an Artisan command (`php artisan platform:grant-admin {email}`).
- A separate `/platform` route group with its own `EnsurePlatformAdmin` middleware, its own controllers, and its own Inertia layout.
- Cross-org listings (all orgs, subscription status) are written as explicit queries: `Organization::query()` is untenanted anyway, and any tenant model uses `withoutGlobalScope(OrganizationScope::class)` **only** inside `App\Platform\*` classes. A Larastan rule or an architecture test (`arch()->expect(...)`) keeps `withoutGlobalScope` out of the rest of the app.
- **Support mode:** to look inside one org, the admin "enters" it. This sets `CurrentOrganization` for their session, shows a persistent banner, and writes a `platform_audit_logs` row (who, which org, when, why). Every write made in support mode is logged too. The normal tenant scope and policies then apply, so support mode shows exactly what that org sees and nothing from other orgs.
- Platform admins are **not** given org roles implicitly. Policies treat support mode as `Admin`-equivalent for that one org.

### 1.10 Build order: players and teams before the form builder

_Potential Planning Phases_ builds the form builder (Step 3) before player management (Step 4). Reversed here. Form submissions must _write into_ `players`/`guardians`, so those models, their validation, and their dedupe rules have to exist first. Doing it this order also means an org can get value (manual entry + rostering) before the hardest feature ships.

Notes on the changes:

- **Soft deletes + unique slugs:** a soft-deleted team still occupies its slug. That's intended: restoring it must not collide. If an admin wants to reuse the slug, the UI offers restore instead.
- **`seasons.start_date` → `starts_on`**, `dob` → `date_of_birth`, `Maps_link` → `maps_url`: descriptive names, consistent `_on` suffix for date-only columns, and no capitalized column.
- **Jersey size** (mentioned in _Potential Planning Phases_) is a per-season uniform-order fact. It lives in the submission data and, if it needs filtering, as a column on `team_player`, not on `players`.
- **`circular FK`**: `organizations.active_season_id` → `seasons` → `organizations`. Create `seasons` after `organizations`, then add `active_season_id` in its own migration.
- **Submission `data` is encrypted.** It holds minors' medical and contact answers, and it is never queried directly. Anything that needs filtering is copied to real columns when the submission is processed (_Initial Research_ §4). Encryption doesn't replace access control.

## Phase 0: Design System & App Shell

**Fonts changed after launch:** Barlow Condensed and Barlow replaced Big Shoulders Display and Public Sans. They're more readable in dense rosters and on phones and keep the scorebook feel.

**Status: built.** The org color isn't applied to `--brand` yet; that waits for the contrast check in Phase 3 branding.

**Goal:** replace the starter kit's look entirely before any product screens are built, so every later phase is built in the new design rather than restyled afterwards. When this phase is done, nothing should be recognizable as the Laravel React starter kit: no left sidebar of cards, no centered-card auth pages, no Instrument Sans, no neutral shadcn grays, no default settings tabs.

### Direction: "Scorebook"

The app is styled after the **paper scorebook** a team keeps in the dugout: ruled sheets, ink on warm paper, numbered columns, and numerals you can read at a glance. It comes from the subject, it suits a product that is mostly rosters and lists, and no generic SaaS template looks like it. It is restrained, not themed: no baseball clip-art, no stitched-leather textures, no cartoon mascots.

The admin app is also used **on a phone at the field**, so density and style never beat legibility in sunlight or touch-target size.

### Foundations

**Type**

| Role    | Face                       | Use                                                                       |
| ------- | -------------------------- | ------------------------------------------------------------------------- |
| Display | **Barlow Condensed** (OFL) | Page titles, the org name, season tile, jersey numbers, scoreboard counts |
| Text    | **Barlow** (OFL)           | Everything else; `tabular-nums` on in tables, dates, and money            |

- Fonts are **self-hosted** as woff2 in `resources/fonts` (no new npm package, no third-party font CDN, so families' IPs aren't sent to a font host).
- Scale: a tight, mostly 4-step scale. Display sizes are large and condensed, body is 15/16px. Column headers are display face at small size, uppercase, with modest tracking. Tracked caps are only used there, never as a logo treatment.

**Color** (defined as `oklch` tokens in `resources/css/app.css`, replacing every starter token)

| Token                 | Light: "Day game"                | Dark: "Night game"                    | Meaning                                     |
| --------------------- | -------------------------------- | ------------------------------------- | ------------------------------------------- |
| `--paper`             | warm off-white (~`#F6F1E7`)      | deep field-at-night navy (~`#0F1620`) | page background                             |
| `--sheet`             | slightly brighter paper          | one step lighter navy                 | content surfaces                            |
| `--ink`               | navy-black (~`#1C2430`)          | chalk white (~`#EDEAE2`)              | text, primary buttons                       |
| `--rule`              | scorebook blue-gray (~`#C9D3DC`) | low-contrast slate                    | table rules, dividers                       |
| `--clay`              | infield clay (~`#B5532C`)        | brighter clay                         | platform accent, focus ring, selection      |
| `--grass`             | deep green (~`#2F5D3A`)          | lifted green                          | success, paid                               |
| `--warn` / `--danger` | mustard / brick red              | lifted equivalents                    | flags, failures                             |
| `--brand`             | = `--clay` by default            |                                       | **overridden by the org's `primary_color`** |

- **Org branding:** inside an org (and on its public pages), `--brand` comes from `organizations.primary_color`. A matching `--brand-ink` foreground is computed server-side (light or dark text, whichever passes contrast). The branding settings form warns when the chosen color can't reach WCAG AA on paper or as a button fill, and offers the nearest color that does.
- Both themes are designed, not inverted. The existing light/dark/system appearance setting is kept.

**Shape and texture**

- Radius is nearly square (2px; 4px max). No pill buttons, no rounded-2xl cards.
- Hierarchy comes from **rules and type, not shadows or card boxes.** Surfaces are separated with 1px `--rule` lines. Shadows only on things that float (menus, dialogs).
- A faint ruled-line background (CSS gradient, no image) on the main sheet, like scorebook paper. It sits behind the content, never behind text inputs, and it's turned off in high-contrast mode.

**Motion:** 120–180ms ease-out for state changes only (row moved, panel opened). No entrance animations, no bounce. Everything respects `prefers-reduced-motion`.

**Icons:** keep `lucide-react` (already installed), 1.5px stroke, used sparingly and always next to a text label in navigation.

### The app shell (replaces `app-shell`, `app-sidebar`, `app-header`, `nav-*`)

- **No sidebar.** A top **scoreboard bar**:
    - Left: the org's logo if uploaded, otherwise the **org name set in display type**. No icon-in-a-chip placeholder.
    - Center: the **season tile**, a scoreboard-style block reading `SPRING 2026 ▾`. It opens the season switcher (links, per decision 1.3). Ended seasons are labelled `FINAL`.
    - Right: org switcher (only shown for users in more than one org), user menu.
- Below it, primary nav as a row of **lineup-card column tabs**: Teams · Players · Registrations · Settings (plus Platform for platform admins). The active tab gets a heavy underline in `--brand`.
- **Mobile:** the bar collapses to org name + season tile, and the primary nav becomes a **bottom tab bar** with 44px+ targets, reachable one-handed in the dugout.
- **Support mode** (decision 1.12) shows as a full-width clay banner above the scoreboard bar that can't be dismissed.
- Page header pattern: large display title left-aligned on the sheet, a one-line context line under it (e.g. "10U · 12 players"), actions right-aligned. Breadcrumbs only on pages three levels deep.

### Surfaces that need their own design

- **Auth pages** (replace `auth-layout`): split layout. The form sits on a ruled sheet on one side; the other side is a big typographic panel. For invitation and claim-account links, that panel shows **the inviting org's name and color**, so people recognize who invited them. On mobile the panel shrinks to a header band.
- **Settings** (replace `layouts/settings/layout`): Profile, Security and Appearance stay separate pages (Security sits behind password confirmation, so they can't share one sheet). They're joined by a numbered section index (01 Profile, 02 Security, 03 Appearance): a row of tabs on phones, a sticky ruled index on desktop.
- **Public org pages and registration forms** (Phases 8 and 10): **the org's brand leads** (its logo, name, and color), and the platform appears only as a small "Powered by nineward" footer. Registration is single-column and mobile-first, with "Step 2 of 4" progress in text. Big tap targets, and autofill-friendly field names.
- **Welcome / marketing page** (replace `welcome.tsx`): a typographic hero set in display type over ruled paper, a single line-score-style row of product facts, a screenshot of the roster builder. Pricing is one flat price.
- **Platform admin** (Phase 2): the same shell, but with an ink-colored scoreboard bar instead of org branding, so it's always obvious you're in the platform area.

### Platform mark

The "nineward" wordmark is set in Barlow Condensed, lowercase. The symbol is drawn from scorekeeping: a **diamond drawn as a single line with home plate filled in**, the scorer's mark for a run that scored. It's used for the favicon and the "Powered by" footer. No icon chip, no tagline under the name.

### Build

1. Replace the tokens in `resources/css/app.css` with the scorebook tokens above (light, dark, and org-accent override). Remove the starter's `--sidebar-*` and `--chart-*` tokens unless a later phase needs charts.
2. Self-host the two font families. Remove Instrument Sans.
3. Restyle the primitives in `resources/js/components/ui/*` (button, input, select, checkbox, dialog, dropdown, badge, toast, skeleton). The Radix behavior and accessibility stay; only the styling changes.
4. Build the new shell (scoreboard bar, column tabs, mobile bottom bar) and delete the starter's sidebar, header, nav, and logo components plus `ui/sidebar.tsx` once nothing imports them. Shared org/season data comes from `HandleInertiaRequests::share()` (Phase 1).
5. Rebuild the auth pages, settings, dashboard, and welcome page on the new shell. The existing Fortify flows are unchanged.
6. New shared components: `DataTable`, `PageHeader`, `SeasonTile`, `LineScore`, `JerseyNumber`, `StatusMark`, `EmptyState`, `LineupCard`.
7. A **local-only component sheet** page (registered only when `app()->isLocal()`) that renders every component and state in both themes, used to review the design before screens are built on it.

### Checks

- Review every page in light and dark at 375px and 1440px wide, using the browser tools.
- WCAG AA contrast for text and controls in both themes and with a sample of org colors. Visible focus on every control. 44px touch targets on mobile.

**Status: built.** Changes from the plan:

They're renamed, and tests check the shared `seasons` prop survives. Factory-generated season and division names also could randomly match names tests spell out, causing rare test failures; generated names can no longer collide.

**Goal:** start a new season in a minute without retyping 20 team names.

### Build

1. **Archiving is just "not the active season"** (decisions 1.2 and 1.3). Nothing moves, nothing is deleted. The master player list ignores seasons entirely (_Season Archiving_ §4: one Johnny, many roster rows).
2. **Rollover wizard** (multi-step Inertia page): name + dates + age cutoff (pre-filled one year on) → "import teams from season X?" (pick which) → confirm. The confirm step previews how many returning players now fall into a higher division by league age, a heads-up for building the new rosters.
3. **`App\Actions\Seasons\RollOverSeason`**, a corrected version of the sample in _Season Archiving_:

    ```php
    class RollOverSeason
    {
        /**
         * @param  array{name: string, starts_on: string, ends_on: string, age_cutoff_on: string}  $attributes
         * @param  Collection<int, Team>  $teamsToCopy
         */
        public function handle(Organization $organization, array $attributes, Collection $teamsToCopy, bool $activate): Season
        {
            return DB::transaction(function () use ($organization, $attributes, $teamsToCopy, $activate): Season {
                Organization::whereKey($organization->id)->lockForUpdate()->first();

                $season = $organization->seasons()->create($attributes);

                $season->teams()->createMany($teamsToCopy->map(fn (Team $team): array => [
                    'organization_id' => $organization->id,
                    'division_id' => $team->division_id,
                    'name' => $team->name,
                    'slug' => $team->slug,
                ])->all());

                if ($activate) {
                    $organization->update(['active_season_id' => $season->id]);
                }

                return $season;
            });
        }
    }
    ```

    What changed from the original sample:
    - The org comes in as a parameter. It isn't read from `auth()->user()->organization_id`, which doesn't exist, and the action works from a console command or a test.
    - Activation is a single FK update. No "deactivate the old row" step can be forgotten or race.
    - The org row is locked so two simultaneous rollovers serialize.
    - Teams are copied with `createMany` through the relationship instead of a loop of `Team::create`.
    - **Rosters are not copied**, as the original intended. Head coach is not copied by default, but it could be offered as a wizard checkbox.
    - The controller handles the redirect. The action returns the season and knows nothing about HTTP or sessions.

4. **Old seasons are read-only by default:** `TeamPolicy::update` / `RosterEntryPolicy` deny edits on teams in seasons that ended, unless the user is an admin. This prevents accidental edits to history.

### Tests

Teams copied with new `season_id` and no roster rows, activation optional, old season untouched, concurrent rollover doesn't produce a broken state, coach can't edit an ended season.

    ```json
    {
        "fields": [
            {
                "id": "f_8k2",
                "type": "text",
                "label": "Allergies?",
                "required": false
            },
            {
                "id": "f_9p1",
                "type": "date",
                "label": "Birth date",
                "required": true,
    ```

Schema validation rejects unknown types, unknown `maps_to`, duplicate ids, and missing required identity fields. Publishing creates a new immutable version. Editing a published form produces a new version and leaves existing submissions pointing at the old one.

## Phase 9: Registration Payments (Parent Pays Org)

**Model (decided):** each org **connects its own Stripe account** and manages it in its own Stripe Dashboard. Registration fees are **direct charges** on the org's account: the org is the merchant of record, its name is on the parent's statement, it pays Stripe's processing fee, and it handles payouts, refunds, and disputes. **The platform takes no cut of registrations.** Our revenue is only the monthly subscription from Phase 2. In Stripe's terms, these are Standard connected accounts with no `application_fee_amount`.

**The platform carries no payment risk:**

- Parents' money goes straight into the org's Stripe account and pays out to the org's bank. It never passes through the platform's account.
- Refunds, disputes, and chargebacks are taken from the org's Stripe balance. The platform's account is never involved.
- Platform revenue is the monthly subscription only, so it doesn't change with how much an org collects.

**What the platform is still responsible for** (operational, not financial):

- **Accurate payment status.** If the app misses or double-counts a Stripe notification, an org could see a paid registration as unpaid. Webhooks are signature-verified and de-duplicated (step 4) to prevent this.
- **Protecting family data.** Submissions hold children's details and parents' contact info. They stay encrypted and isolated per org (decision 1.7, Phase 1).

The app's job is to start Checkout on the org's account and keep `payments` in sync.

This phase can ship after everything else is live.

**Status: built.** Changes from the plan:

- Onboarding uses Stripe account links, which create a new Standard account. Linking an org's _existing_ Stripe account needs Stripe's OAuth flow; that's a possible add-on, not built.
- Families who leave Checkout get a signed "pay now" link (on the thank-you page, in the confirmation email, and copyable from the inbox) that opens a fresh Checkout. Payments gained an `Expired` status for abandoned checkouts, and a partial refund keeps `Paid` with `refunded_cents` set.
- If Stripe is unreachable when a family submits, the registration is still saved and the thank-you page offers the pay link instead of an error.
- The fee is set in dollars in the form's details and copied onto the payment when the family registers. It isn't versioned with the questions: a price change applies to new registrations right away.
- `StripeConnectAccount` isn't tenant-scoped, because webhooks arrive with only the account ID. The webhook handler finds the organization from the account, then sets it as current, so payment lookups stay tenant-scoped and an event can only touch its own organization's payments.
- Connecting, reconnecting and disconnecting are owner-only. Disconnecting in the app pauses fee forms; it doesn't touch the Stripe account.
- Before trying it by hand: set `STRIPE_KEY`/`STRIPE_SECRET`, enable Connect in the Stripe Dashboard, add a Connect webhook endpoint for `/stripe/connect-webhook` (or `stripe listen --forward-connect-to localhost:8000/stripe/connect-webhook`), and put its signing secret in `STRIPE_CONNECT_WEBHOOK_SECRET`.

### Build

1. **Connect onboarding:** `StripeConnectAccountController@store` creates (or reconnects) a Standard connected account for the org and redirects to a Stripe account link. Orgs with an existing Stripe account sign into it there. Only owners can connect or disconnect (policy). Status (`charges_enabled`, `payouts_enabled`) is updated from `account.updated` webhooks. Published forms with a price require `charges_enabled`.
    - **Disconnects:** an org can revoke our access from its own Stripe Dashboard. The `account.application.deauthorized` webhook marks the account disconnected. Paid forms then stop accepting submissions, and owners get a notice to reconnect.
2. **Boundary contract:** `App\Contracts\RegistrationPaymentGateway` with a `StripeRegistrationPaymentGateway` implementation bound in a service provider. This is the external-service boundary where the architecture rules call for a contract. Tests bind a fake.
3. **Checkout:** after `ProcessSubmission`, if the form has a price, create a `Payment` (`Pending`, `amount_cents` **copied** from the form version at submit time) and redirect to a Checkout Session created **on the org's account** (the `Stripe-Account` header / `stripe_account` request option). No application fee. The `payment_id` goes in the session metadata so webhooks can find the row.
4. **Webhooks** on a separate Connect endpoint with its own signing secret:
    - Verify the signature. Record `stripe_event_id` in `processed_stripe_events` **inside the same transaction** as the state change, so redelivered events are no-ops.
    - Handle `checkout.session.completed` → `Paid`, `payment_intent.payment_failed` → `Failed`, `charge.refunded` → `Refunded`/partial `refunded_cents`.
    - Heavy follow-up work (receipts) goes to queued jobs that are **idempotent** with `$tries`/`$backoff` set. Stripe calls use timeouts.
5. **Refunds and disputes happen in the org's Stripe Dashboard.** That's the point of the org owning its account, so the app doesn't need its own refund UI. `charge.refunded` and `charge.dispute.*` webhooks from the connected account update `payments`, so the inbox stays accurate wherever the refund was issued. A "Refund" button that calls the API on the org's account is an optional add-on for later, policy-gated to owner/admin, with the state still finalized by the webhook.
6. **Submission vs payment status:** the old schema's `submissions.payment_status` is replaced by the `payments` table (_Initial Research_ §5 asked for pending/paid/failed/refunded). Admins see an unpaid filter in the inbox.

### Tests

Amount copied at submit time, Checkout created on the org's account with no application fee, webhook signature required, duplicate webhook delivery is a no-op, each status transition (including refunds issued from the Dashboard), paid-form publish blocked until `charges_enabled`, a deauthorized account blocks paid submissions, only owners connect or disconnect. All Stripe traffic faked.

## Cross-Cutting Standards (Every Phase)

- **Authorization:** every controller action is covered by a policy (`Gate::authorize` or Form Request `authorize()`). The tenant scope is the safety net, not the permission system.
- **Validation:** Form Requests with array-syntax rules. Pass `$request->validated()` or `safe()->only([...])` onward, never `$request->all()`. Every `exists` rule on a tenant table includes `->where('organization_id', ...)`.
- **Invariants live in the database:** uniqueness (slugs, jersey numbers, memberships, guardian email) has a unique index. Validation gives the friendly message; the index enforces it.
- **Actions** for multi-step business operations (`CreateOrganization`, `AddPlayersToTeam`, `RollOverSeason`, `ProcessSubmission`), wrapped in `DB::transaction` where they write more than one row. Controllers stay HTTP-only.
- **Queries:** eager load before iterating, `withCount` for counts, deterministic `orderBy` with an `id` tie-breaker on every paginated list, `lazy()`/`chunkById()` for exports and backfills. Lazy loading throws outside production.
- **Enums** for every fixed set (`OrganizationRole`, `Handedness`, `ThrowingArm`, `FormStatus`, `SubmissionStatus`, `PaymentStatus`), TitleCase cases, cast on the model.
- **Config:** Stripe keys, price IDs, and webhook secrets in `config/services.php` via `env()`. Code reads `config()` only.
- **Design:** every screen is built from the Phase 0 components and tokens. No starter-kit components, no one-off colors or radii, and every new page is reviewed in both themes at phone width.
- **Frontend:** Wayfinder for every route call, Inertia `<Form>`/`useForm` for forms, `useHttp` + optimistic updates for in-place edits, deferred props with skeletons for slow data.
- **Migrations:** generated with Artisan, one concern each, immutable once deployed, honest `down()` methods.
- **Tests:** Pest feature tests with factories (and factory states such as `Organization::factory()->subscribed()`, `Player::factory()->forOrganization($org)`) for each phase's behavior and failure modes. Every new tenant route joins the Phase 1 isolation dataset. Run `vendor/bin/pint --dirty --format agent` before finishing any PHP change.
